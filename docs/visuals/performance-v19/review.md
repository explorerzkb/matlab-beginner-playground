# v19 真正屏幕刷新节拍

日期：2026-09-10。环境：Mac / MATLAB R2025b。机器上的孤立 Node 服务仍占满约一个 CPU 核。

本轮修正了一个验收盲区：旧 `runPerformanceCheck` 用每帧完整 `drawnow` 测最大渲染能力，但真正主循环在计划帧后调用 `drawnow limitrate`。MathWorks 文档说明该选项最多只更新 20 FPS；同时，`pause` 会执行等价的完整 `drawnow`。所以旧循环能否显示 45 FPS 依赖 `pause(0.001)` 的隐含刷新，而且每次轮询都可能做无用的完整刷新。

修正后：

- 每个计划游戏帧显式执行完整 `drawnow`；
- 两帧之间使用 `drawnow limitrate` 处理回调，但不把它当成显示帧；
- 删除主循环和序章每次轮询末尾的 `pause(0.001)`，改为不触发绘图的线程让出；
- JVM 第一次调用在计时前完成，不把初始化停顿算入稳态 FPS；
- 新增 `runPacedRenderCheck`，五个场景各自预热 30 帧，再按 45 Hz 执行 5 秒完整屏幕刷新，门槛仍是 40 FPS。

最终工作树统一验收：Code Analyzer 零问题，冒烟、序章和四条输入旅程通过；强制渲染五段 71.1 / 95.5 / 72.6 / 86.1 / 136.8 FPS，最低 71.1 FPS；定速完整刷新五段均为 45.0 FPS。

真实 `startGame('ValidationMode', true)` 主循环从序章进入北湖后无输入持续 10.0 秒，记录 447 个计划且完整刷新的帧，为 44.8 FPS。它验证真正主循环的北湖节拍，不代替其他四段的定速场景检查。
