# 游戏方案默认假设审计 01

更新日期：2026-09-03

状态：**详细审计与历史冲突清单。当前结论先读[当前项目状态与接续入口](current-project-state.md)；本文用于追查尚未冻结的问题，不再作为唯一入口。**

## 一、审计结论

此前的讨论已经确定了一批项目边界，但尚未确定完整游戏方案。最近几轮把“北湖环线”“MATLAB 解曲线”“红方加蓝色力场”“第一圈即可结束、最多三圈”等候选结构写得越来越具体，造成一种已经接近开工的错觉。

这个错觉不成立。后续讨论已经确认二维横向平台视角、两个能力相同的小🍐角色和普通绳连接，但仍有几项会改变整个项目的根问题没有对齐：游戏最主要的快乐来自什么、角色怎样移动、绳的手感如何形成合作、一局为什么继续以及如何结束、MATLAB 与良乡校园究竟承担玩法还是只承担叙事和视觉。

因此，目前可以写“问题验证计划”，不能写完整生产任务计划。生产计划必须建立在明确选择或验证结果之上，否则计划越详细，越可能只是把未经确认的假设批量变成代码。

本文不能证明绝对没有遗漏。它的作用是把当前能够识别的默认假设显性化，并建立持续补充的检查表。后续每次新增机制，都需要说明它来自用户确认、原型证据还是设计者推断。

## 二、2026-09-03 本轮新增对齐结果

用户通过语音输入明确收缩了双人方向。以下语音转写按上下文勘误：“厂方”按“场方”理解，“立场”按“力场”理解，“学员梗”按“校园梗”理解，“用神拴住”按“用绳拴住”理解。

本轮确认：

- 两名玩家各自控制一个游戏角色，两个角色之间由绳连接；
- “一人控制角色、一人控制局部力场”不再作为当前核心双人结构；
- 场、重力方向和其他物理规则仍可以由场景或事件改变，但不默认由某一名玩家长期扮演“场方”；
- 校园梗不必全部变成机制，部分元素可以只承担短暂而清楚的识别笑点；
- 模拟网络断开后弹出 `10.0.0.55`登录界面，是用户明确认为有趣的高优先级事件候选；
- 玩家和观众必须看懂、玩家必须能够操作、体验必须真正有趣；公平不是最高目标，能力或处境不完全公平可以接受。
- 两名角色能力完全相同；绳采用普通绳的直觉，可以互相拖拽；不模拟缠绕和打结，也不让绳断裂；根据语音上下文，允许借绳摆荡。
- 用户最初提出跟随视角，随后已经确认二维横向平台视角；当前采用侧视横向卷轴镜头随玩家移动，不再比较斜俯视或三维背后跟拍。
- 用户允许后续按需进行开放网络素材搜索；若公开网络找不到合适素材，应直接说明缺口并请求用户补充，而不是伪造真实性。
- 方案敲定后，用户可能不在场，届时执行过程应依靠已经确认的方案、显性决策和预先约定的回退规则持续推进，避免在低风险细节上反复等待用户。
- 采用类似《森林冰火人》的二维横向平台视角，排除《神庙逃亡》式背后跟随的三维跑酷视角；允许二维侧视镜头随玩家向前卷动。
- 排除写实人物和写实湖景作为主游戏画风，主画面应采用清楚、夸张、容易辨认动作的二维网页小游戏语言。
- 校园网登录页必须被看成游戏事件，不能让观众误以为演示电脑真的断网或打开了登录网站。
- 性能设计坚持轻量二维：不打开真实网页、不依赖联网、不实时处理整张高清图片、不做绳索缠绕和复杂图像特效。
- 两名主角采用“可爱小生物型”的小🍐：同一物种、同一体型、能力完全相同；不采用写实学生、梨头人或以学生服装为主体的角色方向。具体配色、面部、配饰、角色名和出场方式仍待视觉验证。

“两人用绳连接”是当前选择的双人容器，但尚未证明好玩，也没有自动恢复早期《🍐湖搭子》的整套方案。角色能力相同、绳可相互拖拽、不缠绕、不打结、不断裂并允许摆荡已经确认；绳的数值模型、视角和角色移动方式仍未确定。

## 三、状态定义

- **已确认**：用户明确表达，或者用户对精确复述作出明确认可。
- **偏好或边界**：用户表达了明显倾向，但保留例外，不能写成绝对禁令。
- **候选**：值得继续比较或制作原型，但尚未决定采用。
- **助手假设**：为让方案暂时完整而由 Codex 补出的内容，没有用户确认。
- **待验证**：仅靠讨论不能确定，需要真实观看、试玩或目标电脑运行证据。
- **已撤回**：曾经提出，但后续被用户纠正或明确否定。

## 五、会改变整个项目、目前却没有确认的高影响假设

以下问题不能被低级任务计划掩盖。每一项判断错误，都可能推翻大量代码、关卡和美术。

### H01：游戏最主要的快乐是什么

当前文档默认把“实时合作、互相救援和轻微失控”当作主要快乐，但用户尚未明确选择它作为第一位体验。两名角色的基础能力、体型和物理身份已经确认相同；“公平不是最高目标”只允许即时处境和结果不完全对称，不能重新解释为角色能力不同。其他仍可能成立的核心包括：两人互相制造意外的喜剧、共同掌握一套物理系统、有限时间内追求更好成绩、不断看见校园现实被重新解释，或者由答辩现场本身产生反转。

在这一项没有明确以前，无法判断某个机制是主玩法、辅助变化还是只适合做一次演出。

### H02：作品的基本空间和镜头是什么（基本视角已确认）

用户已经选择类似《森林冰火人》的二维横向平台视角：屏幕左右表示前进和后退，屏幕上下表示真实高度，角色能够在平台上跑、跳、下坠、被绳拖拽和摆荡。排除《神庙逃亡》式从角色背后跟拍的三维跑酷视角，也不采用《王者荣耀》式斜俯视地面移动。

“二维横向平台”与“跟随镜头”并不冲突。当前方向采用侧视横向卷轴：镜头保持从侧面观察，同时跟随两名玩家的中点向前移动。镜头是否需要有限缩放、前向留白和纵向跟随仍属于可调细节，但不再影响二维侧视这一基础选择。

### H03：两位玩家到底控制什么（双人容器已收缩）

用户已经选择“两名玩家各控制一个角色，两个角色由绳连接”作为当前双人容器，不再采用一人长期控制角色、另一人长期控制局部力场。两名角色的基础能力、体型和物理身份相同；仍未确定的是它们采用自由跑跳、自动前进还是其他移动方式，以及绳的具体数值怎样影响两人。

角色类型已经确认是可爱小生物型的小🍐；红蓝点和解曲线控制点仍只是可能的出场叙事，具体轮廓、颜色、脸和名称还要由样张确定。

### H04：两个被绳连接的角色怎样在相同能力下形成不同处境

用户已经确认两名角色能力完全相同，因此不再通过质量、跳跃或技能差异制造固定职业。合作差异只能来自两人的即时位置、绳是否拉紧、谁站在安全地面、谁正在悬空，以及关卡此刻对两人的不同影响。

“第一圈中途交换角色”和“在 500 米处交换”不再有必要，仍只保留为历史假设。公平不是最高目标，指的是结果和处境不必时时对称，不表示角色基础能力可以随意做成不同。

### H05：绳的物理规则是什么，以及场景是否改变全局规则

用户已经选择普通绳：距离小于绳长时绳可以松弛，达到最大长度后绳才传递拉力；绳不承受推力。为保证数值稳定，实现中可以加入玩家难以察觉的少量柔顺和阻尼，但不能表现成明显的橡皮筋。两名角色可以互相拖拽，绳不与障碍发生缠绕或打结，也不在游戏中断裂；允许在一方获得支撑时让另一方借绳摆荡。

仍未确定绳长、拉紧后的力度、地面摩擦、悬空角色的摆荡幅度，以及是否存在主动收绳动作。这些数值会决定互相拖拽是有趣的协作，还是持续抢夺控制权。

场、重力和其他物理规则仍可作为关卡事件改变整个场景，但不由固定的场方玩家操纵。全局重力变化是否进入主玩法、怎样预告以及会不会让两人同时失控，仍需单独判断。

### H06：两名角色如何主动移动，以及绳对操作权的影响

当前尚未确定两名角色是自由跑跳、自动向前、只能调整姿态，还是通过互相拉绳获得主要运动。绳如果太强，一名玩家会感觉自己被另一名玩家遥控；绳如果太弱，合作又可能退化为两个角色并排前进。

这会决定游戏到底像平台游戏、跑酷、合作驾驶、双人摆荡还是共同搬运。

### H07：叙事核心是否真的是“理想解进入真实校园”

“MATLAB 给出理想轨迹，校园加入边界条件，两人走出实际轨迹并提交”是 Codex 提出的候选表达。用户认为开场思想“还可以”，但没有确认整款游戏必须围绕提交解曲线展开。

尚未确定的问题包括：为什么必须向前、谁在要求提交、掉出曲线是事故还是程序本意，以及结算为什么重新成为 MATLAB 数据。若这些问题只靠讲解成立，叙事就没有真正进入玩法。

### H08：北湖是否是整款游戏的空间骨架

北湖一圈约 1000 米和每 100 米标记是真实校园材料；把它们变成一局的环线、进度和检查点则是设计选择。用户只强调目标学生长期生活在良乡，并没有确认整款游戏必须一直绕北湖。

北湖可能是主地图、第一幕、开场现实锚点、结算图形来源，或者只是一组校园场景之一。这个决定会影响游戏是否显得丰富，或是否像把所有梗硬塞到湖边。

### H09：有限游戏具体怎样结束

用户只确认“不能无限，总要有结果”。当前文档进一步假设第一圈可以提交、最多三圈、第三圈强制结束。这些都没有用户确认。

仍未确定：结果是通关或失败、共同分数、各自评价、实际轨迹、校园称号还是某种叙事结局；玩家为什么愿意继续；继续以后获得新规则、难度、内容还是更高评价；失败是否也立刻结算；是否允许主动提前结束。

### H10：一局长度、关卡数量和节奏曲线

文档同时出现过三个 100 米段、完整 1000 米、45—60 秒一圈、2—4 分钟一局、最多三圈。这些数字来自不同阶段，不能拼成一个一致方案。

目前只知道最小单元不超过五分钟且可以很短。真正时长应从核心动作多久开始有趣、多久产生变化、角色是否交换以及课堂演示节奏反推，而不是先定圈数再填内容。

### H11：五秒钩子的具体内容

“正常 MATLAB Figure、常微分方程曲线、两个点、一个点坠落、第二个点改变场”是候选分镜。用户确认的是五秒左右产生疑问，以及 UI 与交互服务叙事，不是这个分镜的每个对象。

开场是否需要观众先认出常微分方程、是否由讲解者点击 `Run`、五秒内是否已经允许玩家操作、异常是坠落还是重力改变，都仍可改变。

### H12：合作、竞争和互相捣乱的比例

当前文档默认纯合作。用户此前以竞速、躲避、成长等游戏为例，但没有明确要求只能合作或不能相互影响。绳连接天然会产生救援、误伤、拖累和故意捣乱；用户已经明确公平不是最高目标，但这些摩擦究竟是快乐来源还是需要限制的挫折，目前没有决定。

### H13：失败、重试和“没有死亡”的具体形式

“破防”“解发散”“回检查点”“失败轨迹变成平台”都属于候选。用户只表达不太喜欢角色死亡。尚未确定失败是否中断当前小段、扣时间、改变世界、直接生成结果，或者根本没有传统失败，只评价最终轨迹。

失败轨迹帮助下一次看似有创意，但也可能鼓励故意失败、增加解释成本或让画面越来越乱，不能默认保留。

### H14：重复游玩的动力

有限结局解决“什么时候结束”，没有解决“为什么再玩”。当前没有确定成绩比较、路线变化、角色交换、事件组合、轨迹留存、校园收集或不同结局。若一局主要靠第一次反转和梗识别，第二次很可能迅速失去吸引力。

### H15：校园元素承担什么功能（原则已部分确认）

用户已经明确：不是每个校园梗都要变成玩法机制，部分元素只需短暂出现并被立即认出。模拟网络断开后出现 `10.0.0.55`登录界面，是当前优先保留的事件候选。

登录页的表现边界进一步确认：它不能像真实浏览器或系统窗口一样取得焦点，而应作为游戏画布内部的二维卡片，以掉落、回弹、游戏音效、角色仍在旁边活动等信号明确告诉观众“这是游戏事件”。玩家不输入真实账号和密码。它可以短暂挡路或成为平台，但具体玩法作用仍未最终确定。

其他校园素材在整款作品中的比例，以及各自只做识别还是进入碰撞和关卡规则，仍需逐项判断。

### H16：画风、镜头跟随与真实素材如何共存

用户要求在生产前确认具体画风和感觉，并在第一次错误风格图后排除了写实人物与写实校园主体。当前主方向是《森林冰火人》式清晰二维网页小游戏语言，但不是复制该作品；尚未确定采用纯平涂、MATLAB 图形元素与平涂混合，还是少量真实网页素材闯入二维世界。

镜头确定为二维侧视跟随，不采用三维背后跟拍。当前候选规则是镜头跟随两名玩家的中点，并向共同前进方向留出更多画面；两人拉开时只做有限缩远，不能无限缩放。镜头需要设置不响应微小移动的稳定区，避免绳子抖动导致整个画面晃动。具体数值仍需在灰盒中调整。

用户提供的校园网登录截图已经保存为 `assets/reference/bit-campus-network-login-2026.png`。其真实的蓝天操场、半透明白框、红色保密标语和蓝绿色按钮共同构成识别感，不应默认被现代化重绘。游戏整体画风需要决定如何容纳这种真实网页，而不是强迫网页服从完全统一的插画风格。

2026-09-03 曾生成一张三栏风格对照图，用户立即判定视觉不对。该图没有进入仓库，也不能作为后续参考。失败原因已经明确：它把绳连接画成两个普通人在湖边走路，缺少跳跃、拖拽和救援等玩法动作；擅自生成欧美钟楼校园而非良乡；把真实校园网页面替换成通用旧式密码框；三栏没有保持同一游戏构图，因而无法比较纯粹的画风差异。

下一次视觉探索不能继续直接生成“概念图”。必须先用无美术的画面骨架确定镜头、角色占屏比例、平台与绳的位置、HUD 和真实登录页如何进入画面；只有骨架得到确认后，才在完全相同的构图上替换视觉语言。

### H17：轻量图形和性能预算

当前性能方向已经收缩为基础 MATLAB 的轻量二维图形：角色使用少量 `patch`或图像对象，绳只画为两名角色之间的一条直线并计算两端约束，平台使用简单碰撞形状，镜头只改变二维显示范围。绳不与场景做连续碰撞、缠绕或打结。

校园网原图保留为档案，运行时另行生成适合屏幕显示的缩小副本，并在进入场景前一次性加载。游戏循环中只更新图片的位置和可见性，不从磁盘重复读取，不做实时模糊、透视、逐像素变形或高分辨率旋转。第一版不需要动态光照、复杂粒子和三维模型。

这些约束使方案在结构上较轻，但仍不能直接承诺目标帧率。MATLAB 图形刷新、同时按键、窗口缩放和素材显示必须在目标 Windows 电脑上实测。

## 七、只能靠运行和试玩回答的事项

| 编号 | 待验证事项 | 不能用什么替代 |
| --- | --- | --- |
| V01 | 五秒内是否真的形成疑问，而不是看起来像 MATLAB 出错。 | 不能用设计者解释或文字分镜替代陌生观众观看。 |
| V02 | 两方是否一眼知道自己控制什么。 | 不能用说明书写得清楚替代首次操作。 |
| V03 | 两名玩家是否持续都有有意义的操作。 | 不能只统计按键次数；需要观察双方是否都在做判断。 |
| V04 | 普通绳是否既能传递合作，又不持续夺走任一玩家的控制感。 | 不能因为角色能到达终点就认定手感成立。 |
| V05 | 两人是否自然沟通、救援、发笑并愿意重试。 | 不能由物理模型理论上存在耦合替代。 |
| V06 | 在能力相同的前提下，位置、绳状态和关卡怎样自然形成不同分工。 | 不能用“公平”这一抽象理由替代实际体验。 |
| V07 | 校园元素是否被当前良乡大二学生立即认出。 | 网络传播数据不能完全替代目标学生确认。 |
| V08 | 核心动作在去掉校园梗后是否仍有最低限度的乐趣。 | 不能用第一次看见梗时的笑声替代重复玩法。 |
| V09 | MATLAB 图形刷新、输入状态、碰撞和关闭清理是否稳定。 | 代码审查和硬件规格不能替代 MATLAB 实际运行。 |
| V10 | 共用键盘是否存在鬼键、焦点丢失和手部拥挤。 | 不能用键位表替代目标笔记本测试。 |
| V11 | Windows 缩放、路径、音频和双击启动是否可靠。 | macOS 或单台开发机运行不能替代目标 Windows 验收。 |
| V12 | R2020b 是否能够运行核心版本。 | “尽量使用旧语法”不能替代冒烟测试；该项也不是首版阻塞条件。 |
| V13 | 登录页事件是否让观众发笑，而不是误以为电脑真的断网。 | 不能只凭页面熟悉度判断，需要在课堂相似场景中观察第一反应。 |

## 八、当前文档中已经发现的冲突和越界

1. 《游戏产品方案 v0.1》仍大篇幅描述两只小梨、弹性绳和三个 100 米事件；它是早期技术基线，不是当前玩法。
2. 《设计理由与第一次自我审查》仍以弹性连接论证“已经较好满足双人合作”，该结论已被后续不对称方案重新打开。
3. 《叙事优先核心方向》写了北湖完整一圈、最多三圈和三种圈层，这些是助手假设，不是已确认需求。
4. 同一批文档同时出现“一局 300 米”和“一圈 1000 米”，没有统一的空间比例。
5. 同一批文档同时出现“2—4 分钟”“45—60 秒一圈”和“120—180 秒三圈”，没有经过核心玩法节奏验证。
6. 第一次模拟盲审只审查了旧版“两点同时跑”的文字分镜，不能为新的“角色加场”方案背书，也不能替代真人测试。
7. “三位参与者 15 秒内明白操作”和“至少两位当前学生认出三个场景”目前只是拟定验收条件，尚未发生。
8. “目标电脑性能不是主要风险”来自用户对电脑够用的确认和规格判断，但准确机器、实际 MATLAB 帧率及键盘输入仍未验证。
9. “基础 MATLAB 即可运行”“Symbolic 可选回退”“不联网”是合理工程方向，但其中“不联网”主要来自可靠性设计，不是用户明确提出的玩法要求。
10. 当前 README 把多个不同阶段文档并列，虽然有状态说明，读者仍可能误把旧方案当成当前需求。生产前需要重整文档入口。

## 九、可能在收缩过程中被丢掉的初始要求和机会

以下内容没有消失，但此前几轮过度集中于开场和力场，存在被遗忘的风险：

- 游戏对普通学生要真正有趣，而不只是概念聪明或答辩时看起来高级；
- 不做需要停下来推理唯一答案的谜题，也不做工程设计或参数实验；
- “眼前一亮”可以来自整款作品的结构、现场呈现或结果，不必全部压在开场五秒和核心机制上；
- 一局应有明确节奏和回报，不能只有不断出现的新物理规则；
- 用户不喜欢怪物和死亡，失败与压力需要保持轻松；
- 校园梗需要近期、主流、一眼能懂，但不应变成梗的陈列柜；
- 物理应成为可感受的因果关系，不等于把尽可能多的力学名词塞进游戏；
- 三位学生最终需要能够运行、讲解和修改一部分内容，而不只是拿到一个黑箱演示；
- Windows 可靠性、共用键盘和视觉素材可替换性是最终交付条件，不能等美术完成后再补；
- 最终作品首先要像一个愿意再玩一次的游戏，其次才是 MATLAB 技术展示。

## 十、在生产任务计划之前真正需要对齐的顺序

1. 用一句不含 MATLAB 术语的话确定玩家在三十秒内反复做什么，以及这件事为什么可能有趣；
2. 确定基本空间与镜头，至少排除不适合的横版、俯视、固定单屏或双视图形态；
3. 确定能力相同的两名角色如何移动，以及普通绳的拉紧、拖拽和摆荡怎样形成核心乐趣；
4. 确定场景是否会改变重力或其他全局规则，以及这些变化如何提前让玩家看懂；
5. 定义一次成功、一次失误和一次救援分别如何发生；
6. 定义最小一局为什么结束，以及玩家为什么愿意继续或重玩；
7. 再决定 MATLAB、北湖和校园元素如何支持以上结构；
8. 在进入生产计划前确认基本画风与镜头感觉；关卡数量、时长、圈数、角色细节和键位仍可随后收缩。

以上顺序不是要求所有问题都靠谈话解决。讨论无法判断的部分应当明确进入对照原型，但原型必须回答一个具体问题，不能把整套候选方案一次做完后再期待玩家给出答案。

## 十一、恢复任务计划的条件

满足以下条件后，才开始写生产任务计划：

- 对 H01—H10 至少形成明确选择、保留的两个对照候选，或者指定由哪一个最小原型裁决；
- 当前主方案能用普通语言描述“谁控制什么、反复做什么、为什么需要对方、怎样算有结果”；
- 一次成功、失败和救援具有可观察的因果链；
- 用户明确知道哪些内容仍然只是试验性假设；
- 旧方案文档被标成历史材料，README 只把审计后的当前入口放在最前面。
