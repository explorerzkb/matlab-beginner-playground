# 当前项目状态与接续入口

更新日期：2026-09-03

这份文件是迁移电脑、开启新任务或交给另一个 Codex 后的首要入口。它只保存当前有效的结论、仍需验证的事项和执行边界。其他文档保留调查证据、设计演变与被否决方案；当旧文档与本文件冲突时，以本文件和时间更晚的用户明确决定为准。

这不是聊天窗口的逐字备份。它的目标是让后续开发者不依赖聊天记录，也能准确继续项目。

## 一、项目要做什么

这是北京理工大学工程力学方向大二学生的 MATLAB 课程大作业。最终作品首先必须是一款两个人愿意实际操作、旁观者容易看懂、短时间内能产生笑点和合作反馈的小游戏；物理与 MATLAB 学习价值应进入运动、碰撞、绳力、数据和程序结构，而不是变成调参数看曲线的演示。

三名学生中，一人有较丰富的 AI 编程经验，另外两人的一般电脑操作经验较少。主要设计和实现工作由 Codex 完成，但最终代码必须方便学生运行、讲解和修改少量内容，不能成为只有生成者能维护的黑箱。

## 二、已经确认的游戏骨架

- 游戏采用二维横向平台视角，类似经典网页横版游戏的空间表达：左右表示前进，上下表示高度，平台、跳跃和落点必须一眼可见。这里不复制任何现有游戏的角色、关卡或美术。
- 镜头随两名角色整体向右平移，跟随对象原则上是两人的中间位置，并向前进方向保留更多可见空间。为了避免画面抖动，需要设置镜头稳定区；两人距离过大时可以有限缩远，但不能无限缩放。
- 两名玩家各自控制一个角色，并默认共用同一把键盘。两名角色能力完全相同，不设置固定的“角色方”和“环境方”。具体键位必须集中配置，并在目标 Windows 笔记本上检查多人同时按键冲突。
- 两个角色由一根普通绳连接，可以互相拖拽和在合适场景中借绳摆荡。绳松弛时不施力，拉直到最大长度后只传递拉力；它不表现成橡皮筋，不缠绕、不打结、不断裂，也不计算与障碍物的复杂接触。
- 玩家角色已经确定为同一物种、同一体型、同一能力的原创“可爱小生物型小🍐”。角色不是写实学生、梨头人、校园动物或纯几何点。具体轮廓、脸、配色、名字和动画风格仍需通过角色样张确定。
- 游戏采用有限结果，不做真正的无限模式。单个最小游玩单元应在约 30 秒至 5 分钟内结束；完整关卡可以由多个短单元组成。具体总时长、关卡数量和结算形式尚未冻结。
- 用户不喜欢怪物和角色死亡。失败优先表现为被拖回、失去节奏、回到检查点或形成一次有趣的结算，不以死亡和打怪作为主要压力来源。

## 三、开场和表达原则

- 开场先出现一个看似正常、略显枯燥的 MATLAB 运行结果，然后在约五秒内出现明显但可理解的不协调，让观众意识到程序正在变成游戏。具体异常可以调整，不能把现有分镜当成冻结脚本。
- 五秒钩子只负责抓住注意力；随后必须尽快用实际动作说明两名玩家分别控制哪个角色、绳如何连接两人、近期目标是什么。不能依靠长说明页解释核心操作。
- UI、按钮、输入和画面变化都应服务于玩家直觉、叙事和节奏。不能为了“打破界面”而强迫每个控件变成关卡，也不能只靠概念聪明掩盖玩法无聊。
- `10.0.0.55` 校园网登录页是优先保留的喜剧事件。它只能作为 MATLAB 游戏画布内部的二维卡片出现，角色和关卡仍应部分可见，并配合掉落、碰撞、回弹或游戏音效，让观众明确知道这是游戏事件。程序不得打开真实网页、连接校园网、获取输入焦点或要求账号密码。
- 登录页原始截图保存在 `assets/reference/bit-campus-network-login-2026.png`。正式运行时应使用预先缩小的副本，保留蓝天操场、半透明白框、红色保密标语和蓝绿色按钮等辨识特征。

## 四、场景和校园内容

游戏主要服务于长期生活在良乡校区的大二学生。校园元素应当近期、主流、容易识别；不是每个梗都要变成玩法机制，短暂出现但能让人会心一笑也有价值。

参考素材库已经精简到后续场景设计最需要的区域：

- 北湖及周边绿化；
- 综合教学楼；
- 文萃楼；
- 东食堂、北食堂；
- 操场；
- 理科教学楼；
- 文博中心；
- 文体中心或体育馆；
- 学生服务中心；
- 校车。

参考库入口是 `assets/reference/liangxiang/INDEX.md`。空间关系以 `assets/reference/liangxiang/spatial-structure.md` 和 `spatial-topology.csv` 为依据；照片只能证明外观时，不得凭一张图臆造建筑之间的相对位置。`assets/reference/` 是 Codex 的设计研究输入，不是 MATLAB 运行时素材。正式游戏资源必须经过提炼并集中放入 `assets/game/`。

北湖、校园网、鹅学长、破防水、`i北理/艾比特`等均是高质量候选，但目前没有冻结成固定关卡清单。旧文档中的“三个 100 米场景”“环湖三圈”“白天—傍晚—考试周夜晚”均为历史候选，不是当前需求。

## 五、视觉方向

- 主体画面不采用写实人物和写实校园照片堆叠，而采用轮廓清楚、动作夸张、适合二维横版玩法的风格。
- 第一轮五种画风预览均得到用户正面评价，因此它们是可用的视觉方向，而不是最终选择：平涂网页游戏、MATLAB 绘图世界、校园漫画、现代像素、剪纸拼贴。
- 现阶段最重要的不是继续生成完整场景，而是先确定小🍐的轮廓、两人区分方式、绳连接位置和动作可读性。角色细节见 `docs/character-direction-01.md`。
- 真实登录页可以作为有意闯入二维世界的异质素材，不必强行重绘成普通卡通弹窗；但正式画面必须通过尺寸、边框、动画和上下文明确其游戏属性。
- 视觉、音效、输入映射和关卡数据必须集中管理，不能散落在物理和主循环代码中。

## 六、技术边界

- 主开发版本为 MATLAB R2025b。R2020b 兼容性不是硬性要求，但不得无理由依赖难以兼容的新功能。
- Windows 是最高优先级平台，最终完成只能以 Windows 实机运行作为关键证据。开发机或 macOS 上运行不能代替 Windows 验收。
- 目标电脑只有核显，但硬件规格足够承担轻量二维游戏。这个判断只是设计预算，不是实测结论。
- 第一版使用基础二维图形、简单碰撞体和少量预加载图片；不使用三维模型、动态光照、复杂粒子、绳与地形连续碰撞、高分辨率图片实时变形或每帧读盘。
- 最终应提供适合普通学生使用的双击启动入口。答辩电脑可以保证安装 MATLAB，因此独立 EXE 不是首版必要条件。
- Symbolic Math Toolbox 可以用于开场或讲解中求解一个简单常微分方程，但不能成为运行游戏的脆弱依赖。若使用，应准备预计算结果或不依赖工具箱的回退路径。

## 七、开发前仍未冻结的高影响问题

以下问题会明显改变玩法或工作量，不能被旧文档中的候选答案偷偷替代：

1. 两名小🍐具体如何移动：自由跑跳、自动前进或更依赖绳的牵引。
2. 绳长、拉紧力度、摩擦和摆荡幅度怎样组合，才能产生合作而不是持续抢夺控制权。
3. 一局的直接目标、关卡结构、结束结果和重复游玩的动力。
4. 北湖是完整地图骨架、其中一幕，还是多个良乡区域之间的一个节点。
5. 全局重力变化是否进入玩法，以及如何预告，避免两名玩家同时失去控制。
6. 最终画风与小🍐的具体视觉设计。
7. 校园事件的正式清单及每个事件只负责识别、叙事还是实际机制。

这些问题可以先用低成本灰盒原型验证，但在证据出现前，不得写成“已经好玩”“已经一眼能懂”或“性能已经通过”。

## 八、实施与验收原则

方案冻结后，Codex 可以连续完成实现并自行处理普通代码错误，不必为低风险细节反复等待用户。出现会改变游戏核心、要求额外权限或费用、涉及真实账号数据、需要不可逆操作，或多个选择会造成明显不同成品时，应暂停并请求用户决定。

首个灰盒应优先验证：双人同时输入是否可靠、普通绳是否好玩、双方是否都有控制感、横向跟随镜头是否稳定、陌生观众能否迅速看懂两人的关系。校园美术和梗不能替代这些验证。

正式验收至少包括：

- MATLAB R2025b 实际启动和完整游玩；
- Windows 目标电脑上的帧率、窗口缩放、路径、音频和关闭清理；
- 一把键盘上的双人组合按键与备用键位；
- 登录页事件不会被误认为真实断网或真实认证窗口；
- 两名首次接触者能够完成一个短场景，并说明绳如何影响双方；
- 学生能够找到启动入口、关卡配置、输入配置和可替换素材位置。

## 十、当前最近一步

当前还没有进入完整游戏开发。最合理的下一步是围绕“可爱小生物型小🍐”制作角色剪影或小规模样张，并在同一套横版灰盒构图中验证两名角色、普通绳、平台和跟随镜头的关系。随后再冻结基础跑跳与绳手感，才值得制作正式校园关卡。
